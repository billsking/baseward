### 三次 100 万行复跑

| 轮次 | 无导出基线 P95 (ms) | 导出期间 P95 (ms) | 边际增量 (ms) |
| ---: | ---: | ---: | ---: |
| 1 | 152.13 | 289.35 | +137.2 |
| 2 | 103.76 | 169.39 | +65.6 |
| 3（本报告） | 95.25 | 209.49 | +114.3 |

- 导出期间事件循环停顿：P95 11.26 ms，最大 18.58 ms（443 次采样，间隔 20 ms）
- 直连在同一时段仍为 P95 1.44 ms，说明数据库与网络仍有余量

### 归因实验

1. **数据库侧竞争**：另起一个进程对同一 MySQL 做 100 万行全表扫描，同时测小表查询——小表 P95 1.46 → 2.91 ms、`SELECT 1` 0.75 → 2.30 ms。数据库不是增量的主要来源。
2. **事件循环饥饿**：导出期间 loop lag P95 11.26 ms、最大 18.58 ms，`YIELD_EVERY=50` 生效，事件循环未被整批编码按住。
3. **版本对照**（同参数、无导出、同一 mirrored 网络）：v1.3 代码 c10 额外开销 141.65 ms，v1.4 为 118.79 ms——v1.4 无 MCP 路径回归，且**两者都超 100 ms**。
4. **网络模式**：mirrored 比 NAT 本身多约 18 ms（同一 v1.4 代码 c10：118.79 vs 100.95 ms）。

### 结论

- 本机（WSL2 + 局域网 MySQL）的无导出基线在 79.65–152.13 ms 之间波动（79.65 ms 为 v1.3 已验收值，见 `docs/perf-report.md`），同一代码、同一参数三次基线相差 15–72 ms。该环境**无法稳定复现 100 ms 阈值**，基线本身就可能不达标。
- 导出通道引入的边际开销为 +65.6…+137.2 ms，集中在网关进程内；数据库竞争与事件循环两项已排除，具体放大机制未定位（基线噪声与导出干扰在该环境下不可分离）。
- 导出通道本身的内存与流式回写无缺陷：内存断言通过、并发吞吐通过、事件循环无饥饿。
- 绝对阈值终判**移至部署机（Linux/Docker）复测**，本报告不作为通过依据。

## 说明

- 客户端在独立进程中消费结果，服务端 RSS 不含客户端缓冲。
- 压测客户端同样是独立进程；与网关同进程时两边抢同一个事件循环，测出来的是客户端自身的排队时间。
- 复测在首个采样点后启动，与导出同时进行；同机对照的两次测量参数一致。
- 判定按绝对口径（网关 P95 − 直连 P95 ≤ 100 ms）；「导出相对基线的增量」只用于归因，不作为替代判据。
- 导出期间每 50 行让出一次事件循环（`app/mysql/streaming.py` 的 `YIELD_EVERY`），否则一批 1 万行的编码会把 MCP 请求按住整批。
