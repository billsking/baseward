# Contributing to BaseWard

Thanks for your interest in improving BaseWard! This document covers the practical side of contributing.

## Development setup

Python 3.12 or newer is required.

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
```

## Tests and lint

```bash
pytest tests/unit -q             # unit tests, no external services needed
ruff check .                     # lint
pip-audit -r requirements.txt    # dependency vulnerability scan (CI gate)
```

Integration tests run against a real MySQL server:

1. Copy `.env.test.example` to `.env.test` and fill in the connection settings.
2. The test account needs `CREATE DATABASE` / `DROP DATABASE` privileges. Tests only create and
   drop temporary databases prefixed with `dbgw_test_*` and never touch anything else — still,
   **never point `.env.test` at a production instance**.
3. Without `.env.test`, integration tests are skipped automatically.

```bash
pytest tests/integration -q
```

## OpenClaw bridge plugin

The TypeScript plugin under `integrations/openclaw-baseward` has its own toolchain:

```bash
cd integrations/openclaw-baseward
npm install
npm test
npm run type-check
```

## Documentation

Every user-facing document exists in two languages: `docs/foo.md` (English) and
`docs/foo.zh-CN.md` (Chinese). Keep both in sync when you change either. The two benchmark
reports under `docs/` are generated by `tests/perf/` and stay Chinese-only by design.

## Commits and pull requests

- Write commit messages in the imperative mood, lowercase, with a type prefix:
  `feat:`, `fix:`, `docs:`, `test:`, `ci:`, `chore:`.
- One logical change per pull request; fill in the pull request template.
- Add a `CHANGELOG.md` entry for user-facing changes.
- Make sure unit tests and lint pass before requesting review.

## Security issues

Do **not** open a public issue for vulnerabilities. Follow the private reporting process in
[SECURITY.md](SECURITY.md).
